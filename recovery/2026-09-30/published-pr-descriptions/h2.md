## Problem

Missing-table and UUID-mismatch paths in `commitToTable` previously returned normally. The enclosing cycle could then advance its control-topic checkpoint, clear buffered file responses, and publish `CommitComplete` although those files were not registered. Restoring the original table afterward did not restore the discarded in-memory response.

## Changes

- Report unresolved table batches to the enclosing commit and throw a private `IncompleteCommitException` before checkpointing, response cleanup, or `CommitComplete` publication.
- Reuse `iceberg.control.commit.max-consecutive-failures` for incomplete full and timeout-partial attempts. Its existing default of `1` terminates on the first failure; larger values allow later-cycle retries.
- Reset the failure streak only after a successful full commit. Successful partial recovery does not reset it; failed partial lookup attempts also increment the partial-failure metric.
- Preserve UUID protection and per-table snapshot-offset deduplication, including healthy tables in a mixed failed batch.
- Reuse local assertion helpers to verify files, snapshot commit IDs and offset summaries, event timestamps, and exact checkpoints. Add a regression for successful partial recovery followed by another failure at the shared retry limit.

No new configuration, dependency, or public API is introduced. Other partial-commit exception handling and dynamic routing's initial missing-table policy are unchanged.

## Recovery Policy

This deliberately changes warn-and-discard behavior to bounded retry followed by coordinator failure. Restore the original identifier and UUID before the retry budget is exhausted. A permanently dropped/replaced table, or responses for different UUIDs under one name, requires operator intervention; increasing the retry limit cannot reconcile those identities.

Successful commits to other tables are not rolled back. Their retained responses are deduplicated on retry only while the required snapshot-offset history remains available. After a restart, recovery also requires retained control-topic records and a suitable starting offset. This PR does not change the reset policy, guarantee recovery after history expires, or bound buffered bytes.

## Problem

A coordinator that has not completed a commit has no control-topic checkpoint. If it consumes and buffers a file announcement, then is replaced, a replacement using `auto.offset.reset=latest` can skip that retained announcement. The worker's source offsets may already be committed, so normal source consumption does not recover the file.

## Changes

- Default the coordinator's control-topic consumer to `earliest`; keep transient worker consumers on `latest`.
- Pass the requested default through `Channel` and `KafkaClientFactory`. Valid Kafka checkpoints still take precedence, and an explicit `iceberg.kafka.auto.offset.reset` overrides the default.
- Preserve the existing per-table snapshot-offset filter and the channel replay guard merged in #17713.
- Exercise committed-only and mixed committed/pending history using independent replacement consumers, including a third coordinator for the final replay.
- Assert exact file locations, snapshot identity/count, consumer checkpoints, commit IDs, and non-null full-completion watermarks through a local assertion helper.

No unconditional seek, new dependency, or public API is introduced.

## Recovery Limits

Recovery requires retained control-topic announcements and, for deduplication, the relevant per-table offset boundary in reachable snapshot history. Ordinary commits do not automatically carry that boundary forward. Expiring its snapshots can permit duplicate file registration during historical replay without a valid Kafka checkpoint. This PR does not implement a durable checkpoint redesign or a missing-boundary policy.

Historical responses are buffered before the per-table filter runs. A large retained history can increase startup time and exhaust heap, and the cost can recur whenever a checkpoint is unavailable. Topic retention is not a heap bound. These constraints are documented with the reset policy.
